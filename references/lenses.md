# 研报视角（lens）

同一批 AI 资讯，不同身份的人关心的点完全不同。lens 决定**重要度怎么加权**和**深度解读往哪个方向写**。默认 `pm`。

每个视角下，给定基础重要度后做 ±1~2 的调整——让真正切中该身份痛点的条目浮到必读区。

---

## 通用评分底线（四个视角都适用）

**基础分只看事情本身**：不看来源名气、标题措辞和讨论热度。来源级别（T1 / T2…）只决定能不能进必读、代表稿用哪条（见 `report-format.md`「信源分级与报道面」），不给分数加减。

**必须正常评价**，不要因为「看着不像大新闻」就压分：

- 论文、技术报告、benchmark 与评测方法
- 小团队或个人的开源发布：看能力和可用性，不看作者是谁
- 非英文来源的一手信息：回溯原文后按实质判断
- 监管、诉讼、安全事件的事实进展
- 负面消息：故障、下架、安全事故、裁员

**必须压住**：命中下表类型的条目，基础分封顶，lens 调整后也不能超过。

| 类型 | 封顶 | 例子 |
|---|---|---|
| 营销、活动预告、招聘、奖学金 | 2 | 大会演讲推荐、Fellowship 招募 |
| 例行小版本（bugfix、零碎小功能） | 3 | 编码工具的例行补丁版本 |
| 汇总稿、newsletter 合集 | 3 | 「本周 AI 十件事」 |
| 厂商操作教程（how-to） | 3 | 「如何在 X 中降级用户角色」 |
| 客户案例、合作 PR | 4 | 「某零售商用 Y 重塑业务」 |
| 只有预告，没有可用产品或数据 | 4 | 「即将推出」「开放 waitlist」 |
| 纯训练技巧，没有可复现收益 | 4 | — |

封顶管的是「类型」：客户案例如果其实是行业级大单（金额、规模足以改变格局），小版本如果其实改了关键行为，就不属于这一类，按实质给分。

## pm（产品经理，默认）

**关心**：产研提效、商业产品机会、竞品动向、可落地的用户价值。

**加权**：
- 上浮：研发提效工具（编码 agent / 工作流自动化）、新产品形态与商业模式信号、大厂产品策略变化。
- 下沉：纯学术理论、底层训练 trick（除非直接降低产品成本）。

**深度解读重点**：
- 启示写「对产研流程能怎么用」——具体到某个环节、某个工具替换。
- 机会信号写「能切什么产品 / 什么付费场景 / 哪个长尾市场」。
- 行动写「本周能做的调研 / 试点 / 竞品对标」。

**GitHub 开源雷达角度**（PM 看开源不是读代码、是读信号）：优先盯 AI 编码 / IDE、Agent 应用与工作流自动化、RAG / 知识库产品、MCP / 插件生态、多模态生成应用、行业场景模板。每个项目问三件事——「这能孵化 / 集成成什么产品价值」「它的火说明什么用户需求被验证」「它会不会成为我的竞品或上游」；挑能直接转化为产品能力、揭示需求趋势、或可能改变竞争格局的项目，🔧 技术细节一句带过、把笔墨放在 🎯 产品与 💡 机会上。

## engineer（工程师 / 技术负责人）

**关心**：能不能用、怎么集成、性能与成本、踩坑与最佳实践。

**加权**：
- 上浮：开源项目与权重发布、SDK/框架/工具链、推理优化、可复现的技术突破、benchmark。
- 下沉：融资/IPO/纯商业新闻（给一行即可）、市场营销向产品发布。

**深度解读重点**：
- 启示写「技术选型影响、集成路径、迁移成本」。
- 机会信号写「能替换现有哪套方案、省多少成本/延迟」。
- 行动写「本周跑通 demo / 起 benchmark / 评估接入」，给具体仓库或命令方向。

**GitHub 开源雷达角度**：优先盯 Agent 框架与编排、推理 / runtime / serving、评测与观测、RAG 数据管线、本地模型与端侧工具、安全权限与沙箱、开发者工具链。每个项目问四件事——「能不能马上接入」「依赖和迁移成本多大」「性能 / 成本收益是否可测」「它会不会改变现有技术选型」；产品噱头少写，重点写架构亮点、成熟度、风险和 benchmark 建议。

## investor（投资 / 战略）

**关心**：市场格局、资本流向、商业化拐点、护城河与竞争。

**加权**：
- 上浮：融资 / IPO / 并购 / 营收数据 / 大客户签约 / 市场份额变化、平台级范式转移。
- 下沉：单点技术细节（除非构成壁垒）、开发者工具的功能更新。

**深度解读重点**：
- 启示写「对赛道格局、估值锚、竞争态势的影响」。
- 机会信号写「哪个细分赛道被验证 / 出现窗口、谁受益谁承压」。
- 行动写「该盯的指标（ARR/NRR/份额）、该跟踪的招股书/财报、可对标标的」。

---

## researcher（研究 / 学术）

**关心**：方法创新、SOTA、可复现性、未解问题与研究方向。

**加权**：
- 上浮：论文（尤其 HF Daily Papers）、新架构/训练方法、评测与数据集、模型能力边界。
- 下沉：产品发布、商业新闻、工具更新（给一行）。

**深度解读重点**：
- 启示写「方法的新意、与现有工作的关系、局限」。
- 机会信号写「打开了什么研究方向、什么问题仍未解」。
- 行动写「值得精读的论文 / 可复现的实验 / 可跟进的 baseline」。

## 边界复核：7–8 分条目二次评分

7 分和 8 分决定一条进不进必读，单次整体打分在这里最容易抖。lens 调整后落在 7–8 分的条目，再做一次五轴评分。复核时先遮住来源名和级别，只看发生了什么。

| 轴 | 0–10 分，问的是 |
|---|---|
| 重要性 sig | 影响面多大：多少人、公司、资金、产品受影响 |
| 新颖性 nov | 是不是新东西：首次出现的能力、形态、事实 |
| 可信度 cred | 证据硬不硬：官方公告、数据、可复现，强于爆料和传闻 |
| 共鸣度 reson | 目标读者会不会关心、讨论、转发 |
| 可行动性 act | 读者本周能不能据此做点什么 |

按内容分类取权重，每行合计 10：

| 内容分类 | sig | nov | cred | reson | act |
|---|---|---|---|---|---|
| `model-release` 模型发布 | 3 | 2 | 2 | 2 | 1 |
| `product-launch` / `dev-tooling` / `agent-infra` | 2 | 2 | 1 | 2 | 3 |
| `research` 前沿研究 | 5 | 3 | 1 | 0 | 1 |
| `business` / `policy-safety` | 3 | 1 | 2 | 4 | 0 |
| 观点、访谈（按内容形态补充） | 1 | 3 | 1 | 4 | 1 |
| 教程、指南（按内容形态补充） | 1 | 1 | 1 | 3 | 4 |

`opensource` 开源生态：权重发布用「模型发布」那行，工具类用「产品」那行。

计算：复核分 = Σ(轴分 × 权重)，满分 100。最终分 = (原分 + 复核分 / 10) / 2，四舍五入取整。例如原分 7、复核分 82，最终 (7 + 8.2) / 2 = 7.6，记 8 分。以最终分决定进不进必读：8 分还要过报道面门槛，7 分进「值得关注」。

## 用法

1. 加工每条时，先按「通用评分底线」定基础重要度，命中封顶类先封顶，再按当前 lens 的加权规则调整，调整后不超过封顶。
2. 调整后落在 7–8 分的，做一次「边界复核」，以复核后的分数分档。
3. 必读区的 so-what 和附录的「启示/机会/行动」三段，全部按当前 lens 的「深度解读重点」来写。
4. 视角只换**侧重与措辞**，不改**事实**——同一条资讯的客观内容对谁都一样。
5. 怀疑打分标准跑偏时，用金标集校准，见下文「校准」。

---

## 校准：打分准不准，用金标集说话

`tests/gold/seed.jsonl` 每行一条样本：`material`（标题、来源、级别、时间、链接、原始摘要）、`gold.bucket`（must / notable / skip / either）、`split`（dev / holdout）、`stratum`（难点类型）。`either` 表示两档都可接受，不计分。

现有 32 条从历史日报和抓取数据整理而来，标了 `needs_review`，只是起步样本。要真正有用，需要读者亲自标到 100–200 条，多收容易判错的难例：爆料、客户案例、例行版本、只有预告的发布。

1. 按本文件给每条 `material` 打分。只看 material，不看 gold，也不翻历史日报。结果逐行写进 `preds.jsonl`：`{"caseId": "...", "importance": 8}`。
2. 跑 `python scripts/gold_eval.py --gold tests/gold/seed.jsonl --pred preds.jsonl --split dev`，看各档查准、查全、混淆矩阵、必读门槛扫描和判错清单。
3. **先改标准，再动门槛**：先看判错条目是哪条规则没写清、没覆盖，改本文件或 `report-format.md`；规则改完 dev 仍系统性偏高或偏低，才考虑调必读门槛。
4. 最后在 `--split holdout` 上复查，确认不是只拟合了 dev。holdout 只用来验收，不拿来调规则。
